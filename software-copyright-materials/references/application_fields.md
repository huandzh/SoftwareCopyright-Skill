# 申请表信息字段

按官网实际表单顺序和字段名：

1. 软件全称（**最高优先级字段**）
2. 软件简称（可选）
3. 版本号
4. 软件分类（应用软件/嵌入式软件/中间件/系统软件/其他）
5. 开发完成日期（YYYY-MM-DD）
6. 开发方式（单独开发/合作开发/委托开发/下达任务开发）
7. 软件说明（原创 / 修改（含翻译软件、合成软件））
8. 发表状态（已发表/未发表）
9. 首次发表日期（已发表时填写，YYYY-MM-DD）
10. 著作权人（复合字段：国家/省市/类型[自然人/法人]/姓名/证件类型/证件号）
11. 权利范围（全部权利/部分权利）
12. 权利取得方式（原始取得/继受取得）
13. 开发的硬件环境（≤50字符）
14. 运行的硬件环境（≤50字符）
15. 开发该软件的操作系统（≤50字符）
16. 软件开发环境 / 开发工具（≤50字符，格式：开发环境: xxx/开发工具: xxx）
17. 该软件的运行平台 / 操作系统（≤50字符）
18. 软件运行支撑环境 / 支持软件（≤50字符）
19. 编程语言（预设按钮选择 + 自定义输入≤120字符）
20. 源程序量（纯数字，单位行，指全部源程序总行数）
21. 开发目的（≤50字符，不能只写软件名称）
22. 面向领域 / 行业（≤50字符）
23. 软件的主要功能（500~1300字，官网当前口径）
24. 主要功能口径（长版 500~1300 字 / 短版 ≤200 字）
25. 软件的主要功能（详细版）（500~1300字长版正文，长版口径下与第 23 项内容一致）
26. 软件的技术特点（官网标签 + 一段 ≤100 字说明；见下）
27. 页数（代码鉴别材料实际页数）

## 字段来源与填写口径

- **软件全称最高优先级**：它同时用于 ① 申请表、② 正式资料文件名、③ 代码 Word 页眉、④ 操作手册标题与页眉。必须在生成业务理解、申请表、操作手册和代码材料之前，用 `confirm_stage.py --stage software-name` 单独确认，确认后不得自行改写、补词或改版本写法。任何一处需要改名，都要四处一起改并重新确认。
- 正式资料文件名、代码 Word 页眉、操作手册标题和正文中的软件名称均以已确认的软件全称为准。
- 软件简称：可选；如有常用简称则填写。
- 版本号必须显式确认；写法（`V1.0` 或 `1.0`）由用户决定，脚本不自动添加 `V` 前缀。如果项目配置中的版本号小于 V1.0，需提醒用户软著首次提交通常写 V1.0，并让用户确认填写哪一个。
- 软件分类：默认选"应用软件"。
- 开发完成日期和首次发表日期：必须使用 YYYY-MM-DD 格式。
- 开发方式：默认"单独开发"，多人合作项目选"合作开发"。
- 软件说明：默认"原创"。
- 发表状态：用户确认已发表或未发表；已发表需附首次发表日期。
- 编程语言、源程序量、功能模块、技术特点：根据项目分析生成。编程语言官网为预设按钮选择 + 自定义输入（≤120字符），预设选项包括 Assembly language、C、C#、C++、Delphi/Object Pascal、Go、HTML、Java、JavaScript、MATLAB、Objective-C、PHP、PL/SQL、Perl、Python、R、Ruby、SQL、Swift、Visual Basic、Visual Basic .Net。
- 源程序量：只填纯数字（不含"行"字），指登记软件全部源程序的总行数（非仅代码材料抽取行数）。
- 页数：只填纯数字，指实际提交的代码鉴别材料页数。默认前 40 页 + 后 40 页模式填写 80；使用 `--slice-pages 30` 时填写 60；整个程序不足目标页数时填写全部代码材料页数。不要填写全部候选源码可估算出的页数。
- 软件开发环境 / 开发工具：≤50字符，格式 `开发环境: <OS>/开发工具: <IDE>`，例如 `开发环境: Windows 11/开发工具: Visual Studio Code`；不要填写 React、Next.js、Vite、TypeScript 等技术栈。
- 开发该软件的操作系统：≤50字符，填写实际开发电脑的操作系统版本。
- 该软件的运行平台 / 操作系统：≤50字符，填写软件运行所在的操作系统或浏览器环境。
- 软件运行支撑环境 / 支持软件：≤50字符，直接列出运行依赖（如 Node.js、npm、浏览器），不加格式前缀。
- 开发的硬件环境：≤50字符，优先读取当前电脑 CPU、内存、硬盘配置作为建议值。
- 运行的硬件环境：≤50字符，默认可沿用开发硬件建议值，也可按实际运行设备填写。
- 开发目的：≤50字符，用一句话说明软件开发目的，不能只写软件名称。
- 面向领域 / 行业：≤50字符。
- 软件的主要功能：官网当前要求 500~1300 字（汉字字符加标点，见正式资料里的 .doc 模板注），脚本默认输出长版正文；不足 500 字或超过 1300 字都会被门禁拦下。
- 主要功能口径：默认"长版"；只有表单明确收短文本时才改成"短版"，此时脚本会按业务理解重新生成 ≤200 字短文本填入"软件的主要功能"，长版正文仍保留在详细版字段。不要用截断长文本的办法充当短版。
- 软件的主要功能（详细版）：500~1300 字长版正文；口径为长版时与"软件的主要功能"内容一致，也是操作手册的功能依据。
- 软件的技术特点：写成「官网标签（可多选，用「、」连接）；一段 ≤100 字的技术特点说明」。官网注为「汉字字符加标点100个以内，所列15个选择跟软件相关的，不在100个字符」—— 标签不计入这 100 个字，只有说明部分受限制；说明写软件的技术能力，**不要出现框架/技术栈名称**（React、Tauri、SQLite 这类是内部实现，登记表不看）。可用标签为 APP、游戏软件、教育软件、金融软件、医疗软件、地理信息软件、云计算软件、信息安全软件、大数据软件、人工智能软件、VR软件、5G软件、小程序、物联网软件、智慧城市软件、网页应用。官网标签列表变化时，同步更新 `scripts/common.py` 的 `TECHNICAL_CHARACTERISTIC_TAGS`。

## 一致性要求

- 软件全称和版本号必须与代码材料、操作手册一致，并能在 `软件名称确认.json` 中找到同一次确认记录。
- 正式代码 Word 页眉软件名称必须与申请表信息中的“软件全称”一致，生成 Word 时以申请表软件全称为准。
- 正式代码 Word 页眉版本号必须与申请表信息中的“版本号”一致，生成 Word 时以申请表版本号为准。
- 主要功能必须来自当前项目，不得沿用范本中的旧项目描述。
- `待用户确认` 字段在正式输出前应尽量替换为确认值；如仍存在，必须写入生成报告。
- 业务理解、代码选择、申请表或最终草稿在用户确认后发生修改时，旧确认必须失效并重新记录，不能只保留一个永久为真的确认标志。

## 官方模板与口径来源

官方表单的字段限制以**模板自带的注记**为准（例如「主要功能（注：汉字字符加标点500字到1300个以内）」「技术特点（注：汉字字符加标点100个以内，所列15个选择跟软件相关的，不在100个字符）」）。这些注记只躺在 `.doc/.docx` 模板里，因此：

1. 拿到模板后先导出字段结构：`pwsh "<SKILL_DIR>/scripts/dump_form_template.ps1" -Path "<模板>" -Out "软件著作权申请资料/草稿/字段口径来源.md"`，把每条注记（含模板里没写右括号的）抄成 `草稿/字段口径来源.md`。
2. 口径变更时**先更新这份来源**，再改 `scripts/common.py` 的常量与门禁说明 —— 这样"为什么是这个字数"永远有据可查。
3. 登记要提交的是模板本身：按 `scripts/fill_application_form.ps1` 填写（默认预演，`-Apply` 才写，模板原件不动），填完用 `-Verify` 逐格回读比对草稿。
4. 草稿里没有的值（证件类型/号码、联系人/电话/邮箱等）**不猜**：脚本会把仍为空的填写位列成清单，交给用户补。

## 摘要刷新

代码材料重抽会改变「项目分析摘要」里的估算页数与注释口径，但用户确认过的登记字段不能被覆盖。用

```bash
<PYTHON> "<SKILL_DIR>/scripts/generate_application_info.py" \
  --analysis .../analysis/project.json \
  --code-manifest 软件著作权申请资料/草稿/代码提取清单.json \
  --business-context 软件著作权申请资料/草稿/业务理解.json \
  --refresh-summary
```

只重写摘要小节；命令会打印需要重记的门禁（`application-fields`、`markdown`）。
